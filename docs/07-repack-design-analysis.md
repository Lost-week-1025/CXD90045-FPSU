# 07 · 回打包的结构性分析

> 本文分析的是**"为什么改一个字节不是局部操作"**，以及这套结构的设计意图。
> **不提供操作步骤，也不提供工具。** 原因见文末。

---

## 一、核心结论

> **这套结构的"可修改性"不是均匀的。**
> 不同位置的改动，影响面、可观测性、定位难度差异极大。

理解这一点，比知道"要重算什么"重要得多 ——
因为前者能让你判断"某处改动是否值得做"，后者只能让你跟着清单走。

---

## 二、影响半径

把包结构按"改动的传播范围"分层看：

```
┌─────────────────────────────────────────────────────────────┐
│ 记录头 / 元信息        → 影响 1 层（L1）      观测：立即      │
├─────────────────────────────────────────────────────────────┤
│ 帧流内部               → 影响 2 层（L1 + L3） 观测：延迟      │
├─────────────────────────────────────────────────────────────┤
│ 分区内文件内容         → 影响 2 层（L1 + L2） 观测：最延迟    │
├─────────────────────────────────────────────────────────────┤
│ 载荷尾部 trailer       → 不参与 L1/L3 的校验语义             │
│                          但决定解密是否成立                  │
│                          观测：表面全过、实际全错             │
└─────────────────────────────────────────────────────────────┘
```

**关键洞察**：验证的"观测点"与错误的"发生点"距离越远，定位成本越高。
trailer 那一行之所以最危险，是因为它的错误**在所有校验里都不可见**。

---

## 三、设计意图反推

每一层为什么在那里？从结构本身能反推出设计者的取舍。

### 3.1 为什么校验分三层，而不是一层

如果只有一层（整包 CRC），那么：

- 任何微小损坏都要重传整包 → 对 300+ MB 的固件不现实
- 分不清"传输坏了"还是"文件不对" → 无法给出有意义的错误

三层分工的结果：

| 层 | 它真正回答的问题 |
|---|---|
| L1 | 这个包完整吗 |
| L2 | 这个分区里的文件对吗 |
| L3 | 这段传输有没有坏块 |

**三者正交**，所以可以分别定位。这是典型的"分层故障隔离"设计。

### 3.2 为什么帧校验是 16 bit 求和，而不是 CRC

求和校验的检错能力弱于 CRC，但它**逐帧独立、可增量计算、实现极简**。

在一个"允许局部重传"的场景里，这个取舍是合理的 ——
它要的不是"防篡改强度"，而是"够用的坏块检测 + 极低的开销"。

> 这个选择给后来的分析带来一个**副作用**（见下一节），
> 但在设计者眼里，那不是它的职责。

### 3.3 为什么 IV 必须放在密文之外

CBC 的 IV 必须是解密方**已知的**。若 IV 在密文之内，解密方无法起步 —— 循环依赖。

所以它必须放在帧流之外的固定偏移上。

### 3.4 为什么 trailer 不参与帧校验

因为 trailer 里含 IV。如果 IV 被帧校验覆盖，那么"改密文"就必须"改 IV"，
而"改 IV"又会"改密文" —— 形成自指矛盾。

**设计上唯一的出路就是：把 IV 排除在帧校验范围之外。**

---

## 四、一个副作用：帧校验可以用作"密钥 oracle"

第 3.2 节提到的"16 bit 求和"选择，加上"逐帧独立"与"帧数量极大"，
产生了一个设计者大概没想到的用途：

> **解密后的冗余校验，天然构成一个密钥候选的判别器。**

判别能力估算：

```
正确密钥：通过率 ≈ 100%          （实测 363,724 / 363,725）
错误密钥：通过率 ≈ 1/65536        （16 bit 校验的随机命中率）

信号 / 噪声 ≈ 65536 倍
```

这个分离度意味着：**候选密钥不需要人工判读，通过率本身就是结论。**

这件事的方法论价值在于 —— 它不依赖任何逆向技巧，只依赖
**"找到解密后数据里独立的冗余校验"** 这个观察。
凡是"解密输出含独立校验"的场合，都可套用。

> 本项目用这个方法在 13 个公开候选密钥中唯一确定了机型映射。
> 具体密钥与映射不在本仓库发布。

## 五、可修改性的边界（结论性判断）

综合以上，这套结构对"修改"的宽容度大致是：

| 修改类型 | 是否结构性可行 | 说明 |
|---|---|---|
| 改包元信息 | 可行但有代价 | 单层失效，可定位 |
| 改分区内文件 | 可行但代价最高 | 双层失效，且 L2 的失败表现隐晦 |
| 改帧流区域的密文 | 边界情形 | 需要同时满足 L1 与 L3，且不能破坏 trailer |
| 改 trailer | 不可行 | 会破坏解密链，且无校验可发现 |

**"可行性"与"安全性"是两件事。**
上表说的是结构上能不能通过校验，不是"改了不会出问题"。

## 六、受控往返验证的方法论

回打包在受控条件下做过完整性往返验证。值得记录的**方法**（而非步骤）是：

### 6.1 三层独立校验，而不是只看最终结果

只验证"升级器接受"是不够的 —— 它可能因为别的原因通过。
所以要**分别**验证 L1、L2、L3，任何一层单独失败都能被发现。

### 6.2 明文级差异比对

这是最有价值的检查方式：**在解密后的明文层面做 diff**。

理由：密文层面任何改动都会因 CBC 雪崩效应而看起来"全都变了"，
无法判断实际改了什么。只有在明文层面，才能确认
"我预期的 N 个字节被改了，其余完全没动"。

本项目实测到：预期的 25 字节改动对应明文 **7 个不连续区段** ——
这个数字本身就是"改动没有扩散"的证据。

### 6.3 自校验优先于下游反馈

先用自己实现的校验器把自己产出的包验一遍，再看下游是否接受。
优势：**错误在产生处暴露，而不是在消费处暴露**。

### 6.4 保留原版做基线

任何比对都需要基线。原版包必须原封不动保存 ——
不仅为了 diff，也为了在出现意外改动时能定位到"哪一步引入的"。

## 七、本仓库为什么不提供重打包工具

回打包的实现做过，往返验证也通过过，但**工具不随仓库发布**。

三条理由：

1. **降低门槛的方式不对**：一个能跑的重打包工具，本质上是把"研究结论"变成了
   "端到端产出能力"。这两者的社会影响不同。
2. **失败不可逆**：这类固件刷入失败会导致相机变砖，而相机往往承载着
   不可重拍的素材。
3. **本项目的目标是理解结构**，不是提供固件修改服务。

保留的取舍：

| 保留 | 不提供 |
|---|---|
| 结构的完整描述 | 端到端重打包实现 |
| 各层的失效模式与定位线索 | 分步操作流程 |
| 只读校验工具（验证，不改写） | 写入/生成类工具 |
| 验证方法论 | 现成可用的产出物 |

**这样既保留了研究的可验证性（别人能复现结论），
又不提供端到端的产出能力。**
