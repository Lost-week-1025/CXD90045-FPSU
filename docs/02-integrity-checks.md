# 02 · 三层完整性校验

> 示意图：`diagrams/03-integrity-layers.svg`

三层互相独立：**覆盖范围不同、算法不同、执行主体不同**。
任何改动必须同时满足全部三层，否则会在某个环节被拒。

## L1 · 整包级 DEND CRC-32

| 项 | 内容 |
|---|---|
| 算法 | 标准 CRC-32（反射多项式 `0xEDB88320`，与 zlib 一致） |
| 初值 / 终值 | `0xFFFFFFFF` / 取反（即标准 zlib 语义） |
| 覆盖范围 | `[0, filesize - 12)` |
| 存放位置 | 文件末 4 字节，**大端** |
| 执行者 | PC 侧升级器 |

覆盖范围之所以是 `filesize - 12`，是因为末尾 12 字节是终止符
`u32be(4) + "DEND" + u32be(CRC32)`，CRC 本身不覆盖自己。

## L2 · 分区内逐文件 `.sum` 清单

| 项 | 内容 |
|---|---|
| 形态 | 每个 `NN00_X` 分区对应一个 `NN01_X_sum` 目录，内含 CSV 清单 |
| 规模 | ZV-E10 共 130 项 |
| 执行者 | 相机侧 |

### 行格式

```
type,crc32hex8,sizehex8,mtimehex,0,0x3e8,owner,group,-1,-1,name,
```

- `type`：`0` = 文件，`5` = 目录
- `crc32hex8`：该文件的 CRC-32，8 位十六进制（目录行为 `ffffffff`）
- `sizehex8` / `mtimehex`：8 位十六进制
- 固定的 `0,0x3e8` 与 `root,root` 是模式与属主字段
- `name`：相对路径，目录行以 `/` 结尾

### 命名规则（易错点）

> **sum 目录名 = 原分区名前 4 位数字的末位减 1，再剥掉 `_sum` 后缀。**

例：`0201_x_sum` ↔ `0200_x`。

这不是"编号 +1"的简单关系，末位减 1 在跨十位时会显得反直觉，实现时容易写错。

## L3 · 帧级 checksum

| 项 | 内容 |
|---|---|
| 粒度 | 每 1024 B 一帧 |
| 算法 | 帧内 16 bit 求和（从 `+2` 起 511 个 LE u16） |
| 覆盖范围 | **仅帧内** |
| 执行者 | 引导 / 更新流程 |

**设计意图是允许局部重传，不是防篡改** —— 因此逐帧独立、不含跨帧链式校验。

## 各层的失效表现（分析结论）

这一节记录的是**"改动会在哪一层以什么形式暴露"**，不是操作步骤。
目的是描述这套结构的设计性质与修改边界。

| 改动位置 | 影响的层 | 失效表现 | 定位难度 |
|---|---|---|---|
| 记录头 / 包元信息 | L1 | 升级器直接拒收 | 易 |
| 帧流内部 | L1 + L3 | L1 通过后，在引导阶段才失败 | 难 |
| 分区内文件内容 | L1 + L2 | 相机侧拒绝，且可能在特定操作时才触发 | **最难** |
| 载荷尾部 trailer | 不参与 L1/L3 校验覆盖的那部分语义 | **表面全部校验通过，但解密后首块为垃圾** | **最隐蔽** |

### 为什么"最难"和"最隐蔽"是这两个

- **L2 难定位**，因为它由相机侧验证，而相机不像 PC 升级器那样给出明确错误码；
  失败可能表现为某个功能不可用，而不是"包无效"。
- **trailer 最隐蔽**，详见下一节 —— 它不参与任何一层校验，所以改错它不会有任何检查提前报错。

## trailer 的设计含义（为什么它必须原样保留）

载荷尾部有一段固定长度的 trailer，不在帧流之内。其中包含 **CBC 的 IV**。

这带来两个设计层面的观察：

### 1. 为什么 IV 存在密文之外

CBC 的 IV 必须是解密方已知的。如果 IV 在密文之内，解密方就无法起步 —— 形成循环依赖。
所以它必然放在帧流之外的一个固定偏移上。

### 2. 为什么这构成一个"不可重加密"的约束

AES-CBC 是**链式**的：任一处密文变化都会向后传播到**所有**后续密文块。
因此对整段载荷重新加密时，位于其后的 trailer 内容也会随之改变 ——
包括里面那个 IV。

IV 一变，解密时**第一块就解成垃圾**，而后续块因为 CBC 的自同步性又是正确的。
这种"只有开头坏掉"的形态非常有特征，也正是排查它的线索。

> 本节描述的是**结构性质**，不是修复步骤。
> 结论层面值得记住的一点是：**这套结构的"可修改性"不是均匀的** ——
> 不同位置的改动，影响面与可观测性差异极大。

## 一个特殊情形：首帧不服从通用规则

实测发现载荷的**第一帧**校验和不遵循通用计算规则，而从第二帧起均符合。

**含义**：首帧是特殊头帧，不能机械地套用通用规则。
这类"特例 + 通用规则"的混合结构在嵌入式固件里很常见，
其存在本身就说明该层校验在设计上并非纯粹的一致性检查。

## 关于本仓库不提供完整重打包流程

回打包在受控条件下做过往返验证（重新生成后三层校验全部通过、明文级差异可控），
但**相关工具不随本仓库发布**。

原因：

1. 完整的重打包实现会显著降低"产出可刷写修改固件"的门槛；
2. 这类固件一旦刷入，失败是不可逆的（相机变砖）；
3. 本项目的目标是**理解结构**，不是提供固件修改服务。

因此本仓库只发布：结构的**描述**、各层的**失效模式**、以及**只读**的校验工具。
这样的取舍保留了研究的可验证性，同时不提供端到端的产出能力。
