# 03 · 索尼私有分区表

> 示意图：`diagrams/04-partition-table.svg`
> 位置：eMMC 用户区偏移 0，长度 4,096 B

## 布局

```
+0x000  u32  magic
+0x004  u32  version
+0x008  u32  n_partition
+0x00C  （其余头部字段）
+0x020  partitions[30]        每项 16 B，共 480 B
+0x200  头部副本（magic / version / n_partition / …）
```

容量是 **30 项**：`0x020 + 30 × 16 = 0x200`，正好填到副本起点。

### 分区项（16 B）

| 偏移 | 字段 | 约束 |
|---|---|---|
| `+0x00` | `start` | 低 9 位必须为 0 |
| `+0x04` | `size` | 低 9 位必须为 0，且非 0 |
| `+0x08` | `type` | 见下表 |
| `+0x0C` | `flag` | `bit0` 有效 |

低 9 位为 0 意味着**对齐粒度 512 B**（扇区）。

## 校验条件

只有三条，且都是"副本一致性"检查：

```
u32[0x000] == u32[0x200]
u32[0x004] == u32[0x204]
u32[0x008] <= u32[0x208]        （无符号比较）
```

> **注意：没有任何 magic 常量比对。**
>
> 也就是说，校验不检查 `magic` 是否等于某个固定值，只检查
> "两份头是否一致" 与 "分区数是否落在容量范围内"。
>
> 这一点是逆向过程中最反直觉的发现 —— 一开始按"一定有魔数表"的思路找了很久。

## `type` 语义

| 值 | 含义 | 说明 |
|---|---|---|
| 0 | raw | 裸数据，无文件系统 |
| 1 | normal | 普通文件系统分区 |
| 2 | WBI | 通过 `wb_register_device` 挂载 |
| 3 | LZP | 压缩分区，映射为 `dnflashaN` |

与包内 `0300_partconf/partinf.conf` 的 30 条记录逐字段对应
（`start,size,type,flag`）。

## 镜像内绝对偏移

```
绝对偏移 = 用户区基址 + start
```

ZV-E10 的用户区基址是镜像内 `0x400000`（此前两个 boot 区各 `0x200000`）。

## 这一项的用途

1. **可以在没有真机的情况下合成一张自洽的 eMMC 镜像** ——
   分区表可程序生成，并可自校验（双头一致 + 分区数范围）。
2. 是搭建离线实验环境（QEMU）的**前置条件**。
3. 解释了"固件包里的分区镜像如何落到 eMMC 的具体位置"，是整条链路最后一环。

## 一点提醒

"校验条件宽松" ≠ "可以随便改"。
分区表决定的是**数据往哪里写**，写错位置会把内容覆盖到别的分区上。
在真机上这一点是不可逆的。合成镜像时请务必先做**偏移自检**（区间不重叠、不越界）。
